# NyaySetu Embedding Versioning Specification

**Project:** NyaySetu
**Module:** RAG Knowledge Base
**File:** `docs/rag/16-embedding-versioning.md`
**Status:** Production Specification

---

# 1. Purpose

Embedding versioning ensures that NyaySetu can identify exactly which embedding configuration produced each vector.

This is essential because changing an embedding model changes the vector space.

---

# 2. Versioned Components

At minimum, version:

```text
embedding provider
embedding model
model revision
embedding dimension
embedding configuration
normalization strategy
```

---

# 3. Example Identity

```text
huggingface/
selected-model/
revision-abc123/
dim-768/
config-v1
```

This represents one embedding configuration.

---

# 4. Embedding Version

Create a logical version identifier:

```text
embedding_version = v1
```

---

# 5. Version Must Be Immutable

Once:

```text
v1
```

is used in production, do not silently change what `v1` means.

A changed model requires:

```text
v2
```

---

# 6. Why Immutability Matters

Suppose:

```text
v1 = Model A
```

and later:

```text
v1 = Model B
```

Historical vectors become impossible to reproduce correctly.

---

# 7. Version Registry

Maintain a registry containing:

```text
version
provider
model
revision
dimension
metric
normalization
created_at
status
```

---

# 8. Example Registry

```json
{
  "version": "v1",
  "provider": "huggingface",
  "model": "selected-model",
  "revision": "abc123",
  "dimension": 768,
  "metric": "cosine",
  "status": "ACTIVE"
}
```

---

# 9. Statuses

Possible statuses:

```text
DRAFT
TESTING
ACTIVE
DEPRECATED
RETIRED
```

---

# 10. DRAFT

Configuration exists but has not passed evaluation.

---

# 11. TESTING

Configuration is being evaluated against the retrieval corpus.

---

# 12. ACTIVE

Configuration is approved for production use.

---

# 13. DEPRECATED

Existing vectors remain valid, but new ingestion should use a newer version.

---

# 14. RETIRED

The version should no longer be used for retrieval or ingestion.

---

# 15. Vector Identity

Vector IDs should include embedding version.

Example:

```text
doc_123_chunk_45_emb_v1
```

---

# 16. Alternative

Store version in metadata:

```json
{
  "chunk_id": "chunk_45",
  "embedding_version": "v1"
}
```

The implementation may use both ID and metadata.

---

# 17. No Mixed Vector Spaces

Vectors generated by incompatible embedding models must not be compared directly.

---

# 18. Query Version Matching

A query must use the same embedding version as the active document vectors being searched.

---

# 19. Retrieval Routing

Conceptually:

```text
Active Embedding Version
        ↓
Query Embedding
        ↓
Matching Vector Index
```

---

# 20. Versioned Index Strategy

Recommended:

```text
nyayasetu-vectors-v1
nyayasetu-vectors-v2
```

or equivalent Pinecone namespace/index isolation.

---

# 21. Namespace Strategy

Namespaces can be used when the Pinecone architecture supports the desired isolation.

Example:

```text
embedding_v1
embedding_v2
```

---

# 22. Index Strategy

Separate indexes may be preferable when:

* dimensions differ;
* similarity metrics differ;
* migration requires independent infrastructure.

---

# 23. Dimension Change

If:

```text
v1 = 768
v2 = 1024
```

do not place both into an index requiring one fixed dimension.

---

# 24. Migration

Embedding migration should follow:

```text
select new model
 ↓
create v2 configuration
 ↓
evaluate
 ↓
create new vector space
 ↓
re-embed corpus
 ↓
validate retrieval
 ↓
switch traffic
```

---

# 25. Dual Indexing

During migration, both versions may temporarily exist:

```text
v1 → production
v2 → validation
```

---

# 26. Shadow Retrieval

A new model can be evaluated without affecting user-facing retrieval.

Example:

```text
User query
 ↓
v1 retrieval → user result
 ↓
v2 retrieval → evaluation only
```

---

# 27. Evaluation Comparison

Compare:

```text
v1 Recall@k
v2 Recall@k

v1 MRR
v2 MRR

v1 citation accuracy
v2 citation accuracy
```

---

# 28. Migration Gate

Do not migrate merely because the new model is newer.

Require measurable evidence of:

* equal or better retrieval;
* acceptable latency;
* acceptable resource use;
* acceptable citation behavior.

---

# 29. Rollback

Rollback should be possible:

```text
v2
 ↓
problem discovered
 ↓
restore v1
```

---

# 30. Rollback Requirement

Keep the old index available until the new system is proven stable.

---

# 31. Historical Audits

Past audits may have used:

```text
embedding_version = v1
```

That information must remain attached to the audit execution.

---

# 32. Audit Reproducibility

A historical audit should identify:

```text
knowledge-base version
embedding version
retrieval configuration
agent version
```

where practical.

---

# 33. Finding Provenance

Each finding should be traceable to the evidence retrieval configuration that produced it.

---

# 34. Retrieval Configuration Version

Embedding version alone is insufficient.

Also track:

```text
top_k
filters
reranker
query transformation
similarity threshold
```

---

# 35. Combined Retrieval Identity

Conceptually:

```text
embedding_version
+
retrieval_config_version
```

defines the retrieval behavior.

---

# 36. Chunking Version

Chunking changes can also change embeddings.

Therefore track:

```text
chunking_version
```

---

# 37. Cleaning Version

If cleaned text changes:

```text
cleaning_version
```

should be tracked.

---

# 38. Full RAG Provenance

A retrieved chunk should ideally expose:

```text
source_version
cleaning_version
chunking_version
embedding_version
retrieval_version
```

---

# 39. Example

```json
{
  "sourceVersion": "doc-v3",
  "cleaningVersion": "clean-v2",
  "chunkingVersion": "chunk-v4",
  "embeddingVersion": "emb-v1",
  "retrievalVersion": "retrieval-v2"
}
```

---

# 40. Version Compatibility

The system should validate compatible combinations.

Example:

```text
embedding v1
requires
dimension 768
+
index v1
```

---

# 41. Invalid Combination

If configuration requests:

```text
embedding v1
+
index v2
```

without compatibility:

```text
FAIL
```

---

# 42. Startup Validation

Production startup should validate:

```text
active embedding model
active index
dimension
metric
namespace
```

---

# 43. Health Endpoint

Example:

```text
GET /health/rag
```

should report whether the active embedding/index configuration is coherent.

---

# 44. Version Metadata in Pinecone

Recommended metadata:

```text
embedding_version
model_id
dimension
```

---

# 45. Version Metadata in Database

The document/chunk indexing record should include:

```text
embedding_version
vector_id
indexed_at
index_name
namespace
```

---

# 46. Indexing Record

Conceptual schema:

```typescript
interface ChunkIndexRecord {
  chunkId: string;
  embeddingVersion: string;
  vectorId: string;
  indexName: string;
  namespace?: string;
  indexedAt: Date;
  status: "INDEXED" | "FAILED";
}
```

---

# 47. Re-Embedding Detection

A chunk requires re-embedding when any embedding-affecting component changes:

```text
source text
cleaning version
chunking version
embedding model
embedding configuration
```

---

# 48. Content Hash

Store a hash of the exact embedding input.

Example:

```text
embedding_input_hash
```

---

# 49. Why Input Hash Matters

If:

```text
same chunk ID
```

but:

```text
text changed
```

the system can detect that the existing vector is stale.

---

# 50. Stale Vector

A vector is stale when its embedding input no longer matches the current canonical chunk.

---

# 51. Stale Detection

Compare:

```text
current_input_hash
vs
indexed_input_hash
```

---

# 52. Stale State

Possible status:

```text
STALE
```

---

# 53. Rebuild Job

A rebuild job should identify:

```text
STALE
FAILED
MISSING
```

vectors and regenerate them.

---

# 54. Full Rebuild

A full rebuild may be required when:

* embedding model changes;
* embedding dimension changes;
* chunking changes globally;
* cleaning rules materially change.

---

# 55. Incremental Rebuild

An incremental rebuild is preferable when only a subset of documents changed.

---

# 56. Rebuild Safety

Do not destroy the current production index before the replacement has been validated.

---

# 57. Blue/Green Vector Migration

A safe strategy:

```text
Blue:
current production index

Green:
new embedding index

validate Green

switch traffic to Green
```

---

# 58. Migration Manifest

Create a manifest containing:

```text
old_version
new_version
source_corpus_version
start_time
completion_time
success_count
failure_count
```

---

# 59. Migration Verification

After migration, verify:

```text
vector count
sample vectors
metadata
retrieval metrics
latency
citation traceability
```

---

# 60. Vector Count Check

Expected:

```text
eligible chunks
≈
indexed vectors
```

Differences should be explainable.

---

# 61. Missing Vectors

Any missing vectors should be surfaced.

---

# 62. Extra Vectors

Unexpected vectors should be investigated for:

* stale data;
* orphaned records;
* duplicate ingestion;
* migration bugs.

---

# 63. Deletion During Migration

Document deletion must be propagated correctly to both old and new indexes while both are active.

---

# 64. Regulatory Version Migration

When a regulation is amended:

```text
old document version
+
new document version
```

may coexist.

Embedding versioning must remain separate from legal-document versioning.

---

# 65. Important Distinction

These are different concepts:

```text
Regulation Version
≠
Embedding Version
```

---

# 66. Example

```text
GDPR-like regulation v5
```

may be embedded using:

```text
NyaySetu embedding v2
```

---

# 67. Model Change Does Not Change Law

Updating the embedding model does not modify the underlying legal source.

---

# 68. Source Change Does Not Necessarily Change Model

A new regulation amendment can be embedded with the same embedding model.

---

# 69. Version Naming

Use clear immutable identifiers.

Example:

```text
emb-v1
emb-v2
emb-v3
```

Avoid names such as:

```text
latest
new
final
final2
```

as historical identifiers.

---

# 70. Active Pointer

A separate configuration may identify:

```text
ACTIVE_EMBEDDING_VERSION=v2
```

The pointer can change while version records remain immutable.

---

# 71. Deployment

Production deployment should load the active version from controlled configuration.

---

# 72. Configuration Example

```env
EMBEDDING_VERSION=v1
EMBEDDING_MODEL=selected-model
EMBEDDING_DIMENSION=768
PINECONE_INDEX=nyayasetu-v1
PINECONE_NAMESPACE=default
```

---

# 73. Secrets

Embedding version configuration is not secret.

API keys and credentials must remain in secret storage/environment variables.

---

# 74. Observability

Every embedding operation should emit:

```text
embedding_version
model_id
duration
status
```

---

# 75. Retrieval Logs

Every retrieval operation should record:

```text
embedding_version
retrieval_version
query_id
top_k
```

without unnecessarily storing sensitive query text.

---

# 76. Error Classification

Useful errors:

```text
EMBEDDING_VERSION_NOT_FOUND
EMBEDDING_VERSION_INACTIVE
EMBEDDING_INDEX_MISMATCH
EMBEDDING_DIMENSION_MISMATCH
EMBEDDING_VERSION_UNSUPPORTED
```

---

# 77. Testing

Tests should verify:

```text
version isolation
dimension validation
index compatibility
query-version matching
migration
rollback
stale detection
```

---

# 78. Migration Test

Test:

```text
v1 corpus
 ↓
v2 re-embedding
 ↓
v2 retrieval
 ↓
rollback v1
```

---

# 79. Historical Retrieval

If historical audit reproduction is required, the system must know which embedding/retrieval version was originally used.

---

# 80. Current Retrieval

Normal production retrieval should use the active version.

---

# 81. Version Retention

Retain old vector indexes according to operational and storage constraints.

Do not delete them immediately after migration if rollback or audit reproducibility requires them.

---

# 82. Retirement

When a version is permanently retired:

```text
mark RETIRED
 ↓
disable retrieval
 ↓
archive metadata
 ↓
delete vectors according to retention policy
```

---

# 83. Acceptance Criteria

Embedding versioning must:

* provide immutable versions;
* identify model revisions;
* track dimensions;
* isolate vector spaces;
* support migrations;
* support rollback;
* detect stale vectors;
* preserve audit provenance;
* support historical reproducibility;
* expose configuration health.

# 85. Final Principle

Embedding versions are part of NyaySetu's auditability.

> **If NyaySetu cannot tell which model produced a vector, it cannot fully reproduce how that evidence was retrieved.**
